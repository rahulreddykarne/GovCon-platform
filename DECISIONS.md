# DECISIONS

Record durable architecture/implementation decisions.

### ADR-001 — Phase 0 stops at foundation primitives
- Phase: 0
- Date: 2026-09-26
- Context: `PHASE_00_FOUNDATION.md` reproduces master §24A and §24, including later review-workflow acceptance criteria. The canonical Phase 0 task list is scaffolding, and the phase boundary forbids ingestion, analysis, JEV decisions, and proposal generation.
- Decision: Phase 0 ships schema, configuration, HTTP, logging, CLI, invite-only auth, server-side sessions, role checks, audit events, optimistic version updates, in-app notification storage, classification, and the AI gateway policy. Quorum progression, the review workspace, and product routes stay in Phases 10 and 14.
- Alternatives considered: Implement the full §24A review state machine now.
- Consequences: Phase 0 acceptance is the five scaffolding checks plus foundation tests. Collaborative review behavior is not claimed as done.

### ADR-002 — One schema, including prose tables the illustrative DDL omitted
- Phase: 0
- Date: 2026-09-26
- Context: Master §5 says every table has `created_at` and `updated_at` unless immutable, while many illustrative `CREATE TABLE` blocks omit those columns. §24A requires sessions, audit history, and notifications. §33 defines `decision_runs`.
- Decision: The initial migration includes §5 tables, `decision_runs`, `user_sessions`, `audit_events`, and `notifications`. Mutable tables have `created_at` and `updated_at` maintained by `govcon_set_updated_at`. Immutable history tables keep their event timestamp and do not have `updated_at`.
- Alternatives considered: Create only the columns written inside each SQL block and add the other tables in later phases.
- Consequences: Later phases alter this schema instead of creating parallel tables. `decision_runs` already exists for Phase 8.

### ADR-003 — Primary keys use identity columns
- Phase: 0
- Date: 2026-09-26
- Context: The illustrative DDL uses `BIGSERIAL`. SQLAlchemy 2 renders `BigInteger` identity columns as `GENERATED BY DEFAULT AS IDENTITY`.
- Decision: Surrogate keys are `bigint` identity columns. `vendors.uei` stays the natural primary key.
- Alternatives considered: Hand-written `BIGSERIAL` so the DDL text matches the spec.
- Consequences: Keys remain bigint and defaulted. No application-visible difference from `BIGSERIAL`.

### ADR-004 — Optimistic version on shared mutable records
- Phase: 0
- Date: 2026-09-26
- Context: §24A forbids last-write-wins for final assessment, approval status, and submission status. Proposal versions are already insert-only.
- Decision: `review_sessions`, `pursuits`, `proposals`, and `submissions` have an integer `version`. `apply_versioned_update` writes `UPDATE ... WHERE version = expected` and raises `StaleRecordError` when the row changed.
- Alternatives considered: Application-only comparison of an in-memory version.
- Consequences: A stale writer cannot commit. Comments stay append-only rows and are not versioned.

### ADR-005 — Argon2 passwords and hashed session tokens
- Phase: 0
- Date: 2026-09-26
- Context: Authentication must be invite-only, with password hashing, logout, inactive-user disable, and role checks. Portal browser tokens must not be stored in PostgreSQL.
- Decision: Passwords use Argon2id via `argon2-cffi` with a 12-character minimum. Application sessions store only the SHA-256 of a random token. Deactivation revokes open sessions. Roles are `owner`, `approver`, `reviewer`, and `read_only`. There is no self-registration command.
- Alternatives considered: Store raw session tokens; use bcrypt; defer auth until the web UI phase.
- Consequences: Logout and disable work without a web UI. Phase 14 reads the same session table.

### ADR-006 — Local bind and AI gateway live in the foundation
- Phase: 0
- Date: 2026-09-26
- Context: §24 requires localhost by default, classification before an external model call, and no secrets in logs or PostgreSQL.
- Decision: `WEB_BIND_HOST` defaults to `127.0.0.1` and rejects `0.0.0.0` unless `WEB_BIND_ALLOW_PUBLIC=true`. Compose publishes Postgres on `127.0.0.1:5432` only. `authorize_external_call` allows `PUBLIC`, follows configuration for `PROPRIETARY`, `FCI`, and `CUI` (all default deny), and always blocks `SECRET_CREDENTIAL`. Log handlers redact assignments, URL passwords, bearer tokens, and configured secret values. `reject_database_secret` refuses SAM/PIEE passwords, portal cookies, MFA secrets, and browser session tokens.
- Alternatives considered: Leave the gateway until Phase 18.
- Consequences: Later model calls go through one gateway. Phase 0 does not call a provider.

### ADR-014 — Audit payloads never store secrets
- Phase: 0
- Date: 2026-09-26
- Context: §24 forbids secrets in logs and PostgreSQL. `audit_events.old_value` and `new_value` are JSONB written by `record_audit`.
- Decision: Callers record only non-secret fields such as email, role, and ids. `record_audit` drops keys whose names contain password, token, secret, cookie, or credential markers, including nested objects, before insert. The invite audit stores email and role only.
- Alternatives considered: Keep the secret key with a `[REDACTED]` placeholder.
- Consequences: A mistaken caller cannot persist a password, password hash, or raw token in the audit table.

### ADR-015 — SAM.gov Get Opportunities contract verified 2026-09-26
- Phase: 1
- Date: 2026-09-26
- Context: Phase 1 requires a live check of the SAM.gov Get Opportunities Public API before coding.
- Decision: Use `GET https://api.sam.gov/opportunities/v2/search`. Authentication is the required `api_key` query parameter. `postedFrom` and `postedTo` are mandatory `MM/dd/yyyy` dates at most one year apart. `limit` is records per page, maximum 1000, and the API default is 1. `offset` is the documented page index starting at 0, so pages are requested as 0, 1, 2. The response envelope is `totalRecords`, `limit`, `offset`, and `opportunitiesData`. `noticeId` is the notice identifier (`noticeid` as a query parameter). `type` is the current notice type and `baseType` is the original type. The public API returns only the latest version and does not publish a separate amendment id. `resourceLinks` are attachment URLs. `description` is a URL that requires the API key to download, not the description body. The opportunities page says daily request limits depend on federal, non-federal, or general roles and does not list HTTP 429. The SAM.gov System Account User Guide states default daily limits of 10, 1,000, or 10,000 requests depending on account type. This client still retries 429 and 5xx through the shared HTTP helper, then fails the run. A page that repeats at least half of the previous page's notice ids fails the run instead of truncating.
- Alternatives considered: Treat `offset` as a record offset because some third-party guides do. Download every description body during the search pull.
- Consequences: Default page size is 1000 so a small daily quota is not spent on the API's one-record default. Description and attachment bytes are not downloaded in Phase 1; the raw search record keeps their URLs. `source_id` is `noticeId`. `source_version` is `postedDate` when SAM sends it. An empty HTTP 404 without a search payload is an error, not an empty success.

### ADR-016 — Snapshot hash and archive sweep
- Phase: 1
- Date: 2026-09-26
- Context: Re-running an unchanged SAM payload must not duplicate opportunities or snapshots, and a changed payload must keep the previous observation.
- Decision: `raw_hash` and `opportunity_snapshots.content_hash` are the same SHA-256 of canonical JSON (`sort_keys`, compact separators) of the opportunity object. An unchanged hash does not insert a snapshot and does not update the current row. A changed hash inserts the snapshot and field-diff events, then updates the current row. The archive sweep is a separate database task: SAM rows still `open` whose `archive_date` is before today UTC become `archived` with a `status_changed` event and no new snapshot, because no payload was fetched.
- Alternatives considered: Write a snapshot for the local archive transition. Hash only a subset of fields.
- Consequences: Source fidelity is the stored raw object. Time passing can archive a row without pretending SAM sent a new payload.

### ADR-017 — Contacts, NSN, quantity, and estimated value
- Phase: 1
- Date: 2026-09-26
- Context: Buyer contacts, NSNs, quantities, and values must be extracted without inventing numbers the notice does not state.
- Decision: Contacts are upserted on `(email, agency_path)` only when both are present, because the unique constraint does not dedupe NULL emails. NSNs are 13-digit numbers with the standard dash groups, or the same shape after an NSN label. Quantity is parsed only from a `qty` or `quantity` label. Estimated values come only from an explicit estimated-value field or from text labeled as an estimated value, cost, amount, or price. `award.amount` is not an estimate.
- Alternatives considered: Infer quantity from any nearby number. Copy the award amount into `estimated_value_min`.
- Consequences: Most SAM search records will have null quantity and estimated value until a later source states them. The first NSN candidate is stored on `opportunities.nsn`; the full candidate list is on the snapshot's normalized document.

### ADR-018 — Deterministic watchlist matching semantics
- Phase: 2
- Date: 2026-09-26
- Context: Phase 2 requires explainable shortlist generation without semantic search, AI bid decisions, or proposal workflow.
- Decision: Matching is rule-hit based. Every non-empty watchlist rule group must pass; values inside a group are OR'd. An empty group is a wildcard and is omitted from the AND chain. Keyword and exclude-keyword checks use case-insensitive whole-word matching so `classified` does not veto `unclassified`. Unknown opportunity estimated values do not fail min/max filters; the value group records `status: unknown` in `matched_on`. Score is the count of passing active groups. `govcon match run` evaluates all enabled watchlists. `govcon match rebuild --watchlist N` re-evaluates one watchlist and deletes stale matches for that watchlist. Match upserts are idempotent on `(opportunity_id, watchlist_id)` and preserve existing `status` on update.
- Alternatives considered: Substring keyword matching. Reject opportunities when value is unknown. Reset match status to `new` on every re-evaluation.
- Consequences: A sources-only watchlist matches every opportunity from the configured sources until targeting arrays are filled in. Phase 3 can alert on `status='new'` matches without reimplementing the engine.

### ADR-020 — DIBBS daily index is the Phase 4 batch source
- Phase: 4
- Date: 2026-09-26
- Context: Phase 4 requires a live check of DIBBS pages, the batch/export mechanism, one real daily fixture, the file layout, access terms, and robots behavior before coding. Individual solicitation HTML pages are out of scope unless required.
- Decision: Ingest the fixed-width index `inYYMMDD.txt` from `https://dibbs2.bsm.dla.mil/Downloads/RFQ/Archive/`, linked from `https://www.dibbs.bsm.dla.mil/RFQ/RFQDates.aspx?category=recent`. The layout verified on `https://www.dibbs.bsm.dla.mil/Rfq/RfqFileDefs.aspx` is 140 characters: solicitation (13), NSN/part (46), purchase request (13), return-by `MM/DD/YY` (8), file name (19), quantity (7), unit (2), nomenclature (21), buyer code (5), AMSC (1), item type (1), set-aside (1), set-aside percent (3). Each line is one opportunity. `source_id` is `solicitation:purchase_request` because one solicitation can list more than one NSN. A 13-digit item-type `1` value is stored as a dashed NSN (`8415-01-392-3228`) and its first four digits are stored in `psc_code` as the FSC. Other item-type `1` values, such as local stock numbers, stay null NSNs. Quantity is the zero-padded integer. Return-by is that calendar date at 23:59:59 UTC because the file has no time. Set-aside stores the one-character code. Buyer code and AMSC are stored on `poc`; there is no email, so no contact row is written. `links.ui` is `https://www.dibbs.bsm.dla.mil/RFQ/RfqRec.aspx?sn={solicitation}`, checked once for `SPE1C126T1698` and not fetched per row. The same SHA-256 snapshot path as SAM applies. An unchanged record does not write a snapshot. A changed record updates the row and writes field events, including `cancelled` when status becomes `cancelled`. Rows are not cancelled merely because a later day's file omits them. `govcon ingest dibbs` takes the newest index on the recent page. `--date` fetches that day's index. `--file` ingests a local file and does not open the network. Original bytes are written to `DATA_DIR/dibbs/`. Requests go through `govcon.http` and wait `DIBBS_REQUEST_INTERVAL_SECONDS` (default 2) between calls. Both hosts require the DoD consent POST (`butAgree=OK`) before the file is returned.
- Alternatives considered: Scrape each RFQ HTML page for buyer email. Download `caYYMMDD.zip` and `bqYYMMDD.zip` on every run. Use the solicitation number alone as `source_id`. Treat a missing next-day line as a cancellation.
- Consequences: NSN and quantity coverage are measured from the index. The 2026-09-25 file, the newest file listed on 2026-09-26, is 523 lines, 521 thirteen-digit NSNs, and 523 quantities. Buyer name and email are not in the index. PDF bytes are not stored. DIBBS rows match through the Phase 2 engine without a matcher change. Phase 5 is not started.

### ADR-019 — Alert digest delivery and deadline re-alert
- Phase: 3
- Date: 2026-09-26
- Context: Phase 3 must surface unalerted new matches without a UI. SMTP is used when email is configured; otherwise the digest is written to `OUTBOX_DIR`. The same match must not be alerted again unless a configured material-amendment condition says so. `PHASE_03_ALERTS.md` has no `⚠️ VERIFY` marker. Master §2 names `smtplib` for alerts. Phase 0 already stores `matches.alerted_at`, match status, `SMTP_*`, `ALERT_EMAIL_TO`, and `OUTBOX_DIR`. Phase 1 already records `deadline_changed` on `opportunity_events`.
- Decision: `govcon alerts digest` sends one HTML message per run. It includes enabled-watchlist matches with `status='new'` and `alerted_at IS NULL`, grouped by watchlist. The message includes title, agency, source, PSC, NAICS, set-aside, deadline, whole UTC calendar days remaining, estimated value only when stored, and the first http(s) source link (`links.ui` first). An empty collection does not send mail and does not write a file. Delivery uses SMTP when `SMTP_HOST` and `ALERT_EMAIL_TO` are both set; otherwise it writes one HTML file under `OUTBOX_DIR`. A failed SMTP send does not fall back to the outbox and does not stamp the match. After a successful delivery, `alerted_at` is set and `new` becomes `seen`. `ALERT_ON_MATERIAL_DEADLINE_CHANGE` defaults to true. When it is true, a `deadline_changed` event newer than `alerted_at` adds one amendment alert and the watermark moves forward. Other field changes do not re-alert. Match status is not reopened. Disabled watchlists are skipped. No alert-history table is added. One `alert_digest_sent` audit row records the channel and match ids. Review notification rows are not created.
- Alternatives considered: One message per watchlist. Treat every snapshot diff as material. Reset match status to `new` on a deadline change. Add an `alert_deliveries` table in this phase.
- Consequences: A crash after SMTP or the outbox write and before commit can deliver the same digest once more on the next run. A successful commit does not. Later phases can add awards, competitors, and bid recommendations to the same renderer. Phase 17 can schedule this command. A sources-only watchlist from Phase 2 can still produce a broad digest until targeting codes are filled in.

### ADR-021 — USAspending award search and pricing rules
- Phase: 5
- Date: 2026-09-26
- Context: Phase 5 must verify the USAspending endpoint, award fields, filters, and pagination before storing award history. Quantity and unit price must stay unknown unless the source states them. The digest from Phase 3 can show recent comps. The awards table already exists from Phase 0.
- Decision: Call `POST https://api.usaspending.gov/api/v2/search/spending_by_award/` with no API key. Contract types are `A`, `B`, `C`, and `D`. `limit` is at most 100. `page` starts at 1 and stops when `page_metadata.hasNext` is false. A page that repeats at least half of the previous page's `generated_internal_id` values fails the run. PSC codes are sent as a list and match prefixes. NAICS codes are sent as `{"require": [...]}` and match prefixes. PSC and NAICS are separate requests because filters are ANDed and a watchlist area is the union of its codes. `date_type` is always set: `action_date` for the first 3-year lookback and for an explicit window, and `last_modified_date` for a later pull that starts one day before the previous successful window end. `generated_internal_id` is `award_id`. `Award ID` is `piid`. `Award Amount` is `total_obligation`. `Base Obligation Date`, falling back to `Start Date`, is `action_date`. The search object is stored in `raw`. The first dashed or NSN-labeled 13-digit value in the description is `nsn`. Quantity and unit price come only from explicit payload keys or from a `quantity` / `unit price` / `unit cost` label. The obligation is never divided by quantity. Set-aside is stored only when the payload already has `type_set_aside` or an equivalent key. `GET /api/v2/awards/{id}/` has set-aside on `latest_transaction_contract_data` and still has no quantity or unit price, so bulk ingest does not call it. Enabled watchlists supply the PSC and NAICS codes. A run with no codes does not call the network. `--file` loads a local search document and does not move the incremental watermark. `price_history`, `price_history_psc`, `award_history_for_agency`, and `top_awardees` read the stored rows. The digest shows up to three comps for the opportunity NSN, or the PSC when that NSN has no rows, and prints unit price only when the column is set. Migration `c3e8a1b74f20` adds view `award_recompete_candidates`: action date at least 18 months ago, and period end missing or within the next 18 months. A later end date stays out of the view.
- Alternatives considered: Fetch every award detail for set-aside. Treat IDV type codes as contracts. Compute unit price as obligation divided by quantity. Page with `last_record_unique_id` instead of `page`. Store a parallel awards table.
- Consequences: Most awards have a null unit price because the verified payloads do not carry one. Set-aside stays null on search rows. A failed run can commit awards from earlier pages in that attempt and does not advance the watermark, so the next run repeats the window. More than 1000 pages fails the run instead of truncating. Phase 6 can compute vendor stats from these rows. Phase 17 can schedule the delta.

### ADR-022 — SAM entity lookup, vendor cache, and competitor buckets
- Phase: 6
- Date: 2026-09-26
- Context: Phase 6 must verify the SAM Entity Management API, fetch vendor details lazily, cache with `fetched_at`, show registration data plus computed award stats, surface likely competitors for an opportunity, and search harvested buyer contacts. Buyer contacts are already upserted during SAM ingest (ADR-017). The `vendors` table exists from Phase 0.
- Decision: Call `GET https://api.sam.gov/entity-information/v3/entities` with the same `api_key` as opportunities. Lookup uses `ueiSAM` and `includeSections=entityRegistration,coreData,assertions,pointsOfContact`. Registration status, CAGE, legal and DBA names, physical address, business types, NAICS, PSC, and points of contact are mapped into the existing `vendors` columns. Opt-out placeholder strings are treated as missing values. `ensure_vendor` refreshes when `fetched_at` is older than `SAM_VENDOR_CACHE_HOURS` (default 24) or when `--refresh` is passed. Award stats (`award_count`, `total_obligation`, top agencies, top PSCs) are computed from stored `awards` rows by `recipient_uei`. `competitor_summary` returns top awardees for the opportunity NSN, PSC, agency path segments, and office. Office is the SAM `office` field or the last segment of `agency_path`. Office matching uses `Award.raw` → `Awarding Sub Agency` and `awarding_agency`. Agency matching tries each dot-separated segment of `agency_path`, longest last. `search_contacts` matches name, agency path, or email with case-insensitive substring search. CLI: `govcon vendors show`, `govcon vendors competitors`, `govcon contacts search`.
- Alternatives considered: Store competitor rows in a new table. Call USAspending per vendor lookup. Match agency only on the full `agency_path` string.
- Consequences: Vendor fetch shares the SAM.gov daily quota. Cached rows avoid repeat API calls within the cache window. Competitor buckets omit dimensions with no stored awards. Public API keys may omit FOUO contact email and phone fields. Phase 7 attachments, AI analysis, and the web UI are not started.

### ADR-023 — DeepSeek API contract verified 2026-09-26 and provider layer design
- Phase: 7
- Date: 2026-09-26
- Context: Phase 7 requires a production AI provider for structured solicitation analysis. The master spec names DeepSeek as the default high-volume analysis provider. ADR-008 verified model IDs but left the provider unimplemented.
- Decision: Verified on 2026-09-26 against https://api-docs.deepseek.com/: the chat completions endpoint is `POST https://api.deepseek.com/chat/completions` using OpenAI-compatible format. Authentication is `Authorization: Bearer <key>`. Current model IDs are `deepseek-flash` (V4.1-Flash, 1M context) and `deepseek-v4-pro` (V4-Pro-0813). Legacy IDs `deepseek-chat` and `deepseek-reasoner` are retired. JSON output mode uses `response_format: {"type": "json_object"}`. Temperature has no effect in thinking mode. Usage reports `prompt_tokens`, `completion_tokens`, `total_tokens`. The provider layer uses `httpx` with a 120-second timeout and goes through `authorize_external_call` before every request. Provider factory returns `DeepSeekProvider` when `DEEPSEEK_API_KEY` is set, raises `NoProviderConfigured` otherwise. The factory design accommodates OpenAI and Anthropic providers in later phases.
- Alternatives considered: Use the OpenAI Python SDK with a custom base URL. Implement all three providers in Phase 7. Call the API without the AI gateway.
- Consequences: A deployment without `DEEPSEEK_API_KEY` gets a graceful warning, not a crash. The provider is stateless. Tests mock the provider and never call the live API.

### ADR-024 — Prompt registry, shared fragments, and the no-hardcoded-prompt rule
- Phase: 7
- Date: 2026-09-26
- Context: §43.1 requires that no production AI task prompt is hardcoded inside a business-service module. §38 defines four shared prompt fragments. §39.1 defines the solicitation analysis prompt. Phase 0 created placeholder prompt files and a loader; Phase 7 must activate them and enforce registry-based loading.
- Decision: Shared fragments (`source_security_rules_v1`, `no_fabrication_rules_v1`, `evidence_rules_v1`, `company_facts_policy_v1`) carry `status: active` and production text from §38. The solicitation analysis prompt (`solicitation_analysis_v1`) carries `status: active` and production text from §39.1, with an `includes` front-matter key listing the three shared fragments it depends on. The renderer resolves includes by name under the prompt root. The registry syncs active source-controlled prompts to `prompt_registry` with hash and version. Business services call `load_prompt_from_disk` or `load_prompt` and never import raw prompt constants. A test (`test_no_hardcoded_prompts_in_business_services`) scans service modules for string constants longer than 200 characters containing "you are".
- Alternatives considered: Full YAML parsing with PyYAML instead of the simple key:value front-matter parser. Inline prompt text in the analysis module.
- Consequences: Prompt changes are version-controlled. Every AI run records `prompt_name`, `prompt_version`, and `prompt_hash`. Activation and rollback are supported via CLI. The front-matter parser uses comma-separated includes instead of YAML list syntax.

### ADR-025 — Attachment ingestion: download, SHA-256, extraction, and dedup
- Phase: 7
- Date: 2026-09-26
- Context: Phase 7 requires downloading source attachments for pursued/reviewing opportunities, computing SHA-256, preserving original files, extracting text (PDF/DOCX/XLSX/plain text), tracking extraction status and errors, and avoiding duplicate downloads of identical content. OCR is optional fallback, not default.
- Decision: `download_attachments` collects attachment URLs from `links.resourceLinks`, `links.attachments`, and `raw.resourceLinks`, downloads each, computes SHA-256, saves original bytes under `DATA_DIR/attachments/<opp_id>/`, and extracts text. Dedup checks `(opportunity_id, url, sha256)` and skips files already stored with the same hash. PDF extraction uses `pypdf`, DOCX uses `python-docx`, XLSX uses `openpyxl`, plain text tries UTF-8 then Latin-1. Extraction status is one of `success`, `partial`, `unsupported`, or `error`. Errors are recorded on the `files` row and never propagated to crash the run. OCR is not performed by default. `process_local_file` supports fixture/offline testing without network calls. Files exceeding `ATTACHMENT_MAX_MB` (default 100) are skipped with a warning.
- Alternatives considered: Use `tika` for all extraction. Download only PDFs. Store extracted text in a separate table. Attempt OCR on every image-only PDF.
- Consequences: Most solicitation PDFs with selectable text extract successfully. Image-only PDFs get `partial` status with a note that OCR may be needed. The Phase 0 `files` table is used without schema changes. Three new Python dependencies are added: `pypdf`, `python-docx`, `openpyxl`.

### ADR-033 — One status gate for every compliance state
- Phase: 9
- Date: 2026-09-26
- Context: §15.3, §15.7, §15.11, §15.12, §15.14 and acceptance criteria 5, 6, 10, 12, 17.
- Decision: `matrix.decide_status` is the only mapping from validation inputs to a state; `apply_decision` and `override_requirement` are the only writers after reconciliation. Order: superseded → human override (unless an amendment made it stale) → deterministic failure (`missing` for artifact requirements, else `needs_review`; AI SATISFIED is recorded as a blocked claim and surfaced as an `ai_claim_blocked` finding) → stale → no source location → blocking reconciliation/conflict flags → validation methods. Methods are `deterministic` (all mapped validators pass), `human`, `proposal_scan`, `ai_validation` and `ai_validation_secondary` (only when citing verified, post-amendment evidence ids). Critical requires two methods; AI-only non-critical requires a configured, calibrated `COMPLIANCE_HIGH_CONFIDENCE_THRESHOLD` (unset by default). No evidence → `unknown`, never `missing`. AI `NOT_APPLICABLE` → `needs_review`. `apply_decision` raises if `satisfied` has no method. Overrides require the `override_compliance` permission (owner/approver), a ≥10-character reason, the expected optimistic version, explicit acknowledgment of any deterministic failure, and write `audit_events`.
- Alternatives considered: Letting the AI validator write statuses; trusting high AI confidence by default.
- Consequences: False SATISFIED requires a human override on record. `compliance_runs.false_satisfied_detected` self-checks every matrix run.

### ADR-034 — Conflicts use version-rank precedence only; amendments invalidate by evidence
- Phase: 9
- Date: 2026-09-26
- Context: §15.9–15.10.
- Decision: Conflicts are detected on parsed values per topic (scoped by CLIN where stated). A numbered amendment outranks the base package and lower amendments; that is the only automatic precedence. Same-document, Q&A-vs-base, SOW-vs-solicitation, or equal-rank conflicts are ambiguous → `conflict_ambiguous` flag + blocking finding. Resolved conflicts mark the older requirement `superseded` with `superseded_by_requirement_id`. After a source change, requirements are marked `stale` when a replaced/removed file sourced them, an amendment change sentence names their topic/section/CLIN/file, a Phase 1 event (deadline/quantity/set-aside) touches their topic, or `amendment_analysis` names them. Linked proposal sections become `stale`. A "COMPLIANCE STATUS CHANGED" finding counts previously satisfied requirements. Stale clears only with evidence recorded after the change or a fresh validator pass/fail. JEV `compliance_and_amendment` re-runs; the `bid_decision` bundle re-runs when material.
- Alternatives considered: Letting AI pick the controlling instruction; marking every requirement stale on any amendment.
- Consequences: Topic matching can over-mark stale (accepted noise). Reopening a completed review is flagged (`review_reopen_required`) for the Phase 10 review workflow rather than performed here.

### ADR-053 — Phase 17 scheduler architecture and chain isolation

- Phase: 17
- Date: 2026-09-27
- Context: Phase 17 requires APScheduler-backed job chains with hard predecessor abort, independent chain execution, and every run visible in `/ops`.
- Decision:
  1. Use `APScheduler>=3.10` with `BlockingScheduler` + `CronTrigger` (UTC). Six chains are registered as independent APScheduler jobs; a failure in one chain never affects another.
  2. Each chain step runs in its own `session_scope` so that a step failure (or the VACUUM step's autocommit connection) cannot corrupt the chain-level session.
  3. Chain execution writes a `scheduler_job_runs` row (migration `b1c2d3e4f5a6`) on start (status=running) and on finish (succeeded/failed). Individual ingest steps continue to write `ingestion_runs` rows via the existing bookkeeping layer.
  4. VACUUM ANALYZE uses a fresh SQLAlchemy connection with `execution_options(isolation_level="AUTOCOMMIT")` because VACUUM cannot run inside a PostgreSQL transaction block.
  5. `step_sam_ingest` returns `status="skipped"` (not "failed") when `SAM_API_KEY` is unset; the chain continues.
  6. `step_analytics_refresh` is a no-op that logs clearly; Phase 15 will replace it.
  7. CLI: `govcon jobs list`, `govcon jobs run <chain>`, `govcon scheduler start`. `govcon status` now shows last run per chain with row counts.
  8. `/ops` shows chain summary panel (latest per chain) + full scheduler run history + ingestion runs.
- Alternatives considered: Use a single session for the entire chain (rejected: VACUUM + step failure corrupts the session). Use `BackgroundScheduler` (rejected: blocking is simpler for a local daemon).
- Consequences: Each step's DB work is committed independently. A step failure is always recorded. The scheduler is started via `govcon scheduler start` or `python scheduler.py`.

- Decision: (1) `tests/test_phase19_testing_gates.py` (87 tests) covers exactly the §25 ACs not already exercised by phase-specific tests: parser/fixture checks, idempotency with correct API calls, snapshot behavior, table-driven matching, AI schema registry coverage, full prompt-library gate, JEV/decision acceptance criteria (§36), quorum policy tests, compliance release gate assertions, proposal immutability, submission model checks, and migration. (2) `tests/fixtures/prompts/` adds 9 subdirectories with representative fixtures for each prompt task class (§43.6). (3) `scripts/smoke.sh` is expanded from the Phase 0 stub to the full §25 smoke spec. (4) `govcon prompts` CLI is extended with `list`, `validate`, `render`, `diff`, and `eval` commands (§25, §43 prompt-library CLI).
- Alternatives considered: Adding all tests to phase-specific test files (rejected: would require editing 18 existing files and create cross-phase coupling). Creating a single monolithic test file with every AC from every phase (rejected: duplicates existing per-phase tests and is fragile to infrastructure differences).
- Consequences: The Phase 19 test file is the authoritative AC checklist for the testing strategy phase. Existing per-phase test files remain unchanged. The compliance release gate is gated by the benchmark replay in `test_compliance_benchmark_passes`.

### ADR-054 — Phase 18 security hardening: foundation from Phase 0; evidence assembled here
- Phase: 18
- Date: 2026-09-27
- Context: §24 (Phase 18) specifies data classification, AI gateway, credential rules, localhost bind, and shared prompt fragments. All five were built in Phase 0 (ADR-006) and Phase 7 (ADR-024) as prerequisites for any live AI call; no security component was deferred.
- Decision: Phase 18 does not re-implement any security primitive. Instead it:
  1. Inspects and confirms the existing infrastructure satisfies every §24 AC.
  2. Creates `tests/test_security_hardening.py` with 54 explicit tests that map each AC to a pytest assertion, including a repository credential scan (`TestRepositoryContainsNoLiveCredentials`) and full gateway pipeline tests (`TestAIGatewayBlocksDisallowedContent`).
  3. Records §24A (collaboration/auth/concurrency) as fully satisfied by Phase 10, avoiding duplicate auth stack.
  4. No new migrations, CLI commands, or runtime modules are required.
- Alternatives considered: Re-implement security from scratch in Phase 18 (rejected: duplicates working Phase 0 code and creates inconsistency). Add a separate security CLI command (rejected: gateway is already called by every AI provider call).
- Consequences: All four §24 ACs are provably satisfied by the test suite without duplication. The security module's public surface (`govcon.security.classification`, `govcon.security.secrets`, `govcon.ai.gateway`, `govcon.logging`) is stable and used by every AI call path. No Phase 18-specific Alembic migration is needed.
